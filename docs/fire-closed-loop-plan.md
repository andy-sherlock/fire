## 0. 一句话

**支付宝、微信账单和投资数据自动流进来，App 持续算出"你还要多久能辞职"，并且每个月告诉你这个日期为什么变了。**

FIRE 在这里指：攒够目标金额，就可以提前辞职去做想做的事。闭环思路在美国已有 FIRE Journey 验证；人民币、支付宝和微信账单、国内基金这个组合，目前没有产品做全。

## 2. 核心：三层计算

1. **提炼**：从原始数据自动算出 4 个数字
   - 真实年开销：最近 12 个月支出，剔除标记为"一次性"的大额开销
   - 真实每月存款：每月实际转进投资账户的钱（**从投资端算**，不用"收入 − 支出"，理由见 5.6）
   - 当前可投资资产：持仓 × 每日收盘价 / 基金净值，不含备用金
   - 资产搭配：纳指、债券、加密货币等各占多少，决定波动大小
2. **计算**：目标 = 年开销 × 倍数（或用户自填），从当前资产出发，每月加上存款，用蒙特卡洛模拟
3. **输出**："大概率还要 X 年（最快 A 年，最慢 B 年）" + 本月变化的原因（归因）

新用户数据不足时：先用估计值，结论标"估算"；导入历史账单可直接跳过。

## 3. 计算规则

所有大数字一律用"今天的钱"（扣除通胀后的购买力）显示，只用一行小字提示到时的账面金额。

| 规则 | 做法 | 为什么 |
| --- | --- | --- |
| 通胀只扣一次 | 用户填名义收益，程序内部减通胀 | 旧版扣两次，把"能撑多久"低估了 12 年 |
| 目标跟着物价涨 | 目标是"今天的 145 万"，14.5 年后账面约 223 万 | 按账面 145 万算会提前 3 年"达标"，实际只值 104 万 |
| 存款可以增长 | 可选：基本不涨 / 跟着物价涨 / 还在往上走（按钮还是滑块待定） | 增长 0% 与 8% 相差约 4 年 |
| 通胀放进高级设置 | 默认值待定（第 14 节） | 按实际收益算，通胀 2% 到 4% 只差约 0.1 年 |
| 不填年龄 | 只说"再攒 N 年"，并显示"这笔钱能撑约 N 年" | 用户不想填年龄和寿命 |
| 波动用蒙特卡洛 | 用历史收益反复随机模拟，给范围和成功率 | 全买纳指：快 10 年 / 中位 14 年 / 慢 24 年 |
| 站稳才算达标 | 连续数月在目标以上，或看 12 个月平均（标准待定） | 首次达标后第二年跌回的概率约 18% |
| 临近终点 | 提醒备好 2 到 3 年生活费的缓冲池 | 单靠多攒 20% 只能把跌回概率降到 13% |
| 波动大的资产打折 | 加密货币默认不计入达标判断（待定） | 避免计划依赖赌博式上涨 |
| 数字不乱跳 | 市值每天更新，FIRE 日期按月或平滑后更新 | 每天重算会让日期前后跳一两年 |
| 变化归因 | 每月说明日期变化来自支出、存款还是市场 | 产品最核心的体验 |

**归因算法**：去掉某一个因素（例如本月定投），重算 FIRE 日期，比较差值；按影响大小排序，套固定句式（"本月最大推手是定投 +3 个月，最大拖累是房租 −1 个月"）。纯本地算术，**不需要 AI**。

### 每笔支出对 FIRE 日期的影响（示例）

假设：每月存 5400，扣通胀后年收益 6%，目标 145 万，基准 14.4 年。

| 发生了什么 | FIRE 日期变化 |
| --- | --- |
| 一顿 300 元的饭（一次性） | 推迟 1.7 天 |
| 一次性多花 1 万元 | 推迟 57 天 |
| 每月固定多花 100 元 | 推迟 140 天 |
| 每月固定少花 500 元 | 提前 1.8 年 |
| 资产 30 万时市场涨 10% | 提前 132 天 |
| 资产 100 万时市场跌 10% | 推迟 304 天 |

结论：偶尔的大花销影响很小，**每月固定开销影响巨大**，越到后期市场影响越大。

### 蒙特卡洛

把未来随机"演"几千上万遍：每一年从历史上真实发生过的涨跌里随机抽一个，看这一遍要多少年攒够；统计分布，给出"最快 / 中位 / 最慢"和成功率。

- 采用 FIRE Journey 的改进：每次**连续抽 5 年**，保留"连跌几年"这类真实剧情，再把长期平均收益调到用户的假设值
- 数据：纳斯达克 100 年度收益；2000 年起年化 8.1%（扣 4% 通胀约 3.9%），1985 年起 14.8%。用哪段待定
- 局限：过去不代表未来；它是"风险地图"，不是预测

| 模块 | 内容 | 免费 / 付费 |
| --- | --- | --- |
| 账单导入 + 消费分析 | 支付宝、微信官方账单 | 免费 |
| 资金用途 | 区分备用金和投资的钱 | 免费 |

| 保险 | 上传保单、看现金价值表；计入 FIRE 的规则未定 | 免费；**第一版是否包含：待确认（建议不含）** |
| 手动 FIRE 计算器 | 用户自己填数字算一个日期 | 免费；**建议只给一个数字，不给区间、归因、情景、自动更新（待确认）** |
| **FIRE 闭环** | 自动汇总所有数据 → 日期、区间、每月归因、情景模拟、月度提醒 | **年费** |
| **AI 省钱报告** | 哪些支出可省、省下来能早多少 | **按份 / Plus** |

设计原则：

- 先有数据再出结论；没有数据前，结论标注"示例"或"估算"
- 第一屏只留少数必填项，其余收进高级设置，默认值替用户定好
- 计算在本地完成；不卖基金、不拿佣金
- 首次导入后，只问 2 个问题（"现在大概有多少可投资的钱？""每月大概能存多少？"），让第一份报告能算出 FIRE 日期（待确认）

## 5. 数据接入

### 5.1 单一数据源原则

**每条付款渠道只认一个数据来源。不做随手记，不做截图记账，不做两套数据去重。**

| 付款渠道 | 唯一数据源 |
| --- | --- |
| 支付宝付款（不管绑哪张卡） | 支付宝官方账单 |
| 微信付款（不管绑哪张卡） | 微信官方账单 |
| 直接刷卡、现金 | 月底问一个问题："这个月不走支付宝和微信的消费大概多少？"填一个总数 |
| 已在用其他记账 App 的人 | 可改为导入该 App 的导出文件，但与官方账单二选一 |

为什么够用：通过支付宝、微信付款时，不论绑哪张卡，都会记在支付宝、微信账单里（"收/付款方式"一列标明用的哪张卡）。换卡拿优惠也不影响。真正需要银行账单的只有：直接刷卡、银行自动扣款、银行转账，用月底那个问题兜底。

### 5.2 每月流程（目标 3 分钟）

1. 导入：拖入支付宝、微信账单，自动翻译格式，识别内部转账、买基金、还信用卡（不算开销）
2. 回答最多 5 个问题：大额是不是一次性？某笔转账是什么？不走支付宝和微信的消费大概多少？
3. 看结果："这个月离自由近了 N 天，原因是……"；单独列出每月固定扣费；开销异常偏低时提醒

### 5.3 导入格式："翻译官"架构

1. 定一个**最小统一格式**，引擎只认它：日期、金额、类型（支出 / 收入 / 内部转账 / 投资 / 退款）、对方、来源、唯一编号、是否一次性
2. 每种格式一个翻译器：支付宝、微信、咔皮记账、钱迹、蜜蜂记账
3. 没见过的格式：用户指一次"哪列是金额、哪列是日期"，保存为模板
4. 去重：按交易订单号；没有订单号时按"同日期 + 同金额 + 同对方"

已知细节：

- 支付宝 CSV 为 GBK 编码，开头有说明行。字段：交易时间、交易分类、交易对方、对方账号、商品说明、收/支、金额、收/付款方式、交易状态、交易订单号、商家订单号、备注
- 微信可导出 CSV / XLSX
- 可导出的记账 App：咔皮记账（非会员可导出基础 CSV）、钱迹、蜜蜂记账（开源，BSL 许可，商业使用需授权）

### 5.4 转账怎么处理（不让"自己转给自己"算成开销）（提议，待确认）

核心问题：微信提现到自己的银行卡、支付宝转到自己的卡，在账单里像一笔"支出"，但钱并没有花掉。

按顺序判断，前一步能判断的不进下一步：

| 步骤 | 规则 | 例子 | 结果 |
| --- | --- | --- | --- |
| 1 | 账单自带"不计收支"标记的，直接排除 | 支付宝"不计收支"；微信收/支列为"/" | 零钱提现、余额宝转入转出、信用卡还款 → **内部转账** |
| 2 | 对方名字 = 账户本人名字 | 支付宝转账到"本人"银行卡 | **内部转账** |
| 3 | 主格子、辅助格子之间互转（两边账单金额、时间对得上） | 自己的大号转小号 | **内部转账** |
| 4 | 买基金、转证券账户 | 蚂蚁财富买入、银证转账 | **投资（算存款，不算开销）** |
| 5 | 转给别人的小额转账、红包 | 请客、AA、发红包 | 默认**开销**；同一个人当月转回来的钱相互抵消（AA） |
| 6 | 转给别人的大额转账（超过门槛，如 2000 元） | 转给房东、借给朋友 | 进月底问题："这笔是开销 / 借出 / 给自己 / 投资？" |
| 7 | 记住答案 | 以后转给同一个人的同类转账 | 自动套用，不再问 |

待验证：支付宝、微信账单中"不计收支"等标记和账户本人姓名的实际字段，要用真实账单核对。

### 5.5 投资数据（待确认）

账单能识别"钱进了投资"，但看不到"现在持有多少"。建议：

- **持仓允许手动，但只记份额**（不记每笔交易）；定投自动进行，一个月改一次即可；价格由后台自动更新
- **每月存款**从账单识别：买基金、转券商；月底问题里确认"这笔转到券商的钱是投资吗？"
- 与单一数据源原则的关系：原则针对"消费"，持仓是低频的少量数字，不构成冲突

### 5.6 为什么每月存款从投资端算

漏记的开销会让结果偏乐观。示例（每月存 5400、目标 145 万）：

| 漏记开销 | 存款从投资端算 | 存款按"收入 − 支出"算 |
| --- | --- | --- |
| 2% | 算早 71 天 | — |
| 5% | 算早 180 天 | 算早 331 天 |
| 10% | 算早 366 天 | 算早 650 天 |
| 20% | 算早 754 天 | — |

从投资端算，漏记只影响目标，误差减半。开销漏记要控制在 5% 以内，尤其是每月固定开销。

## 7. 开发路线

### 7.1 技术路线

用**网页技术（Vue）**写，从第一天就按 App 设计，最后用 **Capacitor** 打包成 iPhone App。同一套代码，不返工。

三条规矩：

1. 计算引擎是纯 JavaScript，不碰界面
2. 手机专属功能（分享导入账单、推送、内购）先留插口，用假数据代替，打包时再接上
3. 网页只当内部预览（GitHub Pages），不对外、不收费

体验要求：页面少；按 iPhone 习惯交互（左滑返回、底部标签栏）；离线打开即出结果；不能有"网页感"。

背景：大公司多用原生（Swift / SwiftUI），跨平台常见 React Native、Flutter；网页 + 壳在中小型 App 中常见。所有 iPhone App 最终都经过 Xcode 打包。安卓以后再说（国内要软著、App 备案，且要分别上传华为、小米、OPPO、vivo 等商店）。

| 装到自己的 iPhone | 不需要 | 免费 Apple ID + Xcode，每 7 天重装一次 |

## 8. AI 省钱报告

| 部分 | 要不要 AI |
| --- | --- |
| FIRE 日期、"本月推手 / 拖累"、"每月少花 X 能早几天" | 不要，本地算术 |
| 判断哪些支出"不必要"，写成有温度、具体的建议 | 要 |

- **接入方式**：调用已备案的大模型 API（DeepSeek、通义等）；中间放一个**云函数**（阿里云函数计算、腾讯云云函数或 Cloudflare Workers），保管 API Key、校验付款后再调用
- **成本**：每份约输入 5,000 tokens + 输出 2,000 tokens；DeepSeek V4-Flash 约 ¥0.03，V4-Pro 约 ¥0.1（2026-08 后价格，高峰时段）
- **顺带的好处**：AI 报告必须经过云函数，是唯一绕不过去的付费点
- **隐私**：只发脱敏汇总（如"外卖月均 1,850，比 6 个月前 +22%"），不发每笔明细和交易对方；发送前弹窗展示内容，用户同意后再发
- **合规**：调用已备案模型、面向国内公众，需到省级网信办做"登记"（比备案轻；对输出加工过重可能被要求备案）。报告只谈支出和储蓄习惯，**不推荐任何基金、股票**（证券投资咨询需要牌照）

## 10. 一人一号：格子规则

原则：**算的是"这个人"什么时候能 FIRE，不是某个银行账户。** 别人的数据进来，伤害的是用户自己的计划，靠利益约束而不是靠警察。不追求 100% 防作弊（账单表头可被手改），只要作弊不划算。

| 规则 | 内容 |
| --- | --- |
| 登录 | 通过 Apple 登录；不要手机号、不要身份证 |
| 主格子 | 支付宝、微信各 1 个；各自**第一份有消费记录的账单**所属账户自动成为主格子 |
| 两个独立按钮 | **「删除这份账单」**和**「更换主账户」**是两个功能，用户自己选，互不依赖 |
| 删除账单 | 主格子里的账单最多删 3 次（传错文件时用）；删账单不解除主格子绑定。3 次是总共还是每年：待确认 |
| 更换主账户 | 一年 1 次（例如原账户被封）；**原账户数据保留**，继续算作这个人的历史数据 |
| 重复导入 | 按交易订单号自动去重，不消耗删除次数 |
| 辅助格子 | 其他账户的账单自动进辅助格子；**算进用户的 FIRE**；增删不限次数；进入时提示"加入后 FIRE 日期从 X 变为 Y，要保留吗？" |
| 主大于辅 | 辅助格子消费总额**不能超过**主格子（含历史主账户）；超过时不接受，提示"是不是主账户选错了？"。比较的时间范围（建议最近 12 个月）待确认 |
| 指纹 | 用账单表头的账户信息生成哈希，服务器只存哈希，写进隐私政策 |
| 免费报告 | 按账户指纹计，一个账户一辈子 1 次 |
| 注销账号 | 必须提供（法律和苹果审核要求），注销时删除全部数据；**注销后能否保留"领过免费报告"的哈希：待验证（找专业人士）** |
| 特殊情况 | 邮件或在线客服人工处理，写在帮助页 |
| 适用范围 | 单份报告、年费、Plus 三档 |

为什么够用：

- 轮流换主格子放客户：一年只能换 1 次，且旧数据不删，客户数据互相混在一起
- 用空壳账户占主格子、辅助格子轮流放客户：主大于辅，客户数据最多和空壳一样少
- 删空主格子：只有 3 次
- 重装 App：主格子绑定和报告额度在服务器上，重装不能重置
- 为几块钱钻这些空子不划算，这类人可以忽略

待验证：支付宝、微信账单表头的真实字段（微信可能只有昵称，改昵称会被识别为新账户）。

## 13. 已否决的方案（及原因）

> 以后讨论到这些时，先看这里的原因，没有新理由就不重开。

### 界面与计算

| 否决的方案 | 原因 |
| --- | --- |
| 一打开就显示结论（v10 的做法） | 没有用户数据时显示的是默认数据的结论，会误导 |
| 必填年龄、规划寿命 | 用户不想填；改用"再攒 N 年"和"能撑约 N 年" |
| 只填一个"可投资资产"数字 | 存款每月在变，必须来自真实数据 |
| 通胀扣两次（v9） | 计算错误 |
| 每天重算 FIRE 日期 | 日期会随涨跌前后跳一两年；改为按月或平滑 |

### 数据接入

| 否决的方案 | 原因 |
| --- | --- |
| iPhone 快捷指令截图记账（轻点背面 → 识别 → 写入） | 每笔都要手动触发；支付宝、微信改版后规则要跟着改；FIRE 只需按月、误差 5% 以内的数据 |
| 自己做完整记账功能 | 记账是红海；我们的长处是 FIRE 引擎和归因 |
| 内置"快速记一笔" | 同上，被单一数据源原则取代 |
| 随手记 + 月底导入账单去重的混合方案 | 给用户两条路，用户只会走更省事的那条；两套数据去重会拖垮开发 |
| 存款按"收入 − 支出"算 | 漏记开销时误差翻倍（见 5.6） |
| 银行直连（类似 Plaid） | 国内没有开放银行接口 |
| 安卓无障碍、通知监听自动记账 | 属于截图 / 实时记账路线，已否决 |

### 平台与开发

| 否决的方案 | 原因 |
| --- | --- |
| 只做网页产品 | 后来决定做 App；网页改为内部预览 |
| 先做公开网页、再改成 App | 要返工，还要迁移网页用户 |
| 直接用 Swift 写原生 App | 现有代码和引擎是 JavaScript，不能复用；云端开发环境是 Linux，没法编译和测试 Swift，看进度要靠 Mac；门槛高 |
| 微信小程序 | 个人主体不能做金融、理财类目，不能记录股票、基金 |
| 安卓优先 | 国内安卓要软著、备案、跑五六家商店 |

### AI 接入

| 否决的方案 | 原因 |
| --- | --- |
| 自己电脑部署模型当服务器 | 不能关机；家庭网络一般没有公网 IP；断网停电就不能用；涉及备案 |
| 租 GPU 云服务器部署开源模型 | 每月几千元级别，没人用时也在花钱 |
| 模型跑在用户手机或浏览器里 | 要下载几个 GB；小模型中文理财分析质量差；老手机跑不动 |
| API Key 直接写在 App / 网页里 | 会被偷，别人拿你的钱用 AI |

### 收费

| 否决的方案 | 原因 |
| --- | --- |
| 按次付费查看 FIRE 日期 | 查看的边际成本是 0；用户会憋着不看（出租车计价器效应），收入反而比年费少 5 到 10 倍；经常看到进度正是产品价值 |
| 月付 | 订一个月、看一眼、退订（看完就退） |
| 终身 / 买断（含早鸟限量 ¥198、¥399） | 新 App 没有信任基础，没人会先付终身；终身服务是无上限负债（且吸引最长期的用户）；无上限的权益可被转卖；价格离年费太近会把年费变成诱饵 |
| 首版价格：年费 ¥68、Plus ¥88 | 年费太低；配合 ¥198 买断时，买断 2 年多就回本，结构反了 |
| 每年 1 月免费"年度 FIRE 体检" | 会给免费用户"等到 1 月"的理由；被"首份免费报告"取代 |
| 把 FIRE 数字打马赛克当诱饵 | 廉价，让用户觉得被耍 |
| AI 报告按季度发放、过期作废 | 健身房模式，靠用户忘记使用赚钱 |
| 广告、卖基金、导流理财产品 | 利益冲突，毁信任 |
| 焦虑推送、"即将涨价"话术 | 用焦虑换钱，长期烧光信任 |
| 激活码（面包多、爱发电） | 只是网页版收款的绕路办法；付款步骤多；不能自动续费；改用苹果内购 |
| 网页阶段收费 | 网页只做内部预览，收费从 App 开始 |
| TestFlight 内测收费、私下转账换内测资格 | 违反苹果规定 |

### 防滥用

| 否决的方案 | 原因 |
| --- | --- |
| 身份证实名认证 | 身份证号是敏感个人信息，合规风险大；吓跑诚实用户；每次认证要付费 |
| 传了第二个人的账单就让数据"变乱" | 惩罚的是手滑的诚实用户，看起来像 bug |
| 每号 2 个支付宝 + 2 个微信、90 天锁定、姓名比对 | 规则太多；被"主格子 + 辅助格子"取代 |
| 激活码绑定 2 台设备 | 不再使用激活码 |
| 辅助格子新账户每年上限、"有数据"门槛（1 个月 10 笔） | 被"主大于辅"取代 |
| 更换主账户时清除原账户数据 | 计算的是"这个人"，账户被封不该丢数据 |
| 原账户数据"永远不清除" | 违反删除权和苹果注销要求；改为"换账户不删，注销全删" |
| 先删除再更换的连锁操作 | 删除账单和更换主账户是两个独立按钮 |
